## Context

Vidoc 已跑通「粘贴链接 → 摘要」全流程（见 `openspec/specs/video-summary/spec.md`），但**没有任何计量**。同时线上套餐页（`nuxt-web/app/utils/plans.ts`）已经在卖「1000 积分」「2000 积分/月」——**前端在售卖后端不存在的概念**。本次把积分体系落地，作为后续支付模块的地基。

动机与范围见 `proposal.md`；行为契约见 `specs/points/spec.md` 与 `specs/video-summary/spec.md`。本设计只说明"怎么做"。

## Goals / Non-Goals

**Goals:**
- 余额读写与流水规模无关（O(1)），且任何重试/补偿/并发都不会重复发放或重复扣减。
- 三本账的有效期与结转策略各自独立；**付费买到的积分永不作废**（合规底线）。
- 日切与过期不依赖定时任务（少一个能挂的组件）。
- 存量用户零迁移成本即可使用。
- 支付模块只留接缝。

**Non-Goals:**
- 不做支付渠道对接、不建订单表（用户明确搁置）。
- 不做管理后台、不做人工补发界面。
- 不做订阅到期提醒的推送。
- 不改套餐页「50 条历史记录容量」那条同样尚未实现的承诺。
- 不做积分与真实 token 的逐次精算（见 D9）。

## Decisions

### D1 两张表分工：物化余额 + 展示型流水

- `user_points`（一用户一行）是**唯一真源**，三个分项 + 合计。
- `points_ledger` 降级为**展示与追溯用的历史**，不再承担算余额的职责。

理由：第一版把余额做成「流水求和」，查询要扫该用户**全部未过期流水行**。一个用了一年的活跃用户可能上千行，虽然仍是毫秒级，但它是 O(n)；物化后恒定 O(1)，且**流水从此可以自由裁剪而不影响正确性**。副作用更好：以后改扣费规则不用再担心历史流水怎么解释。

### D2 三本账与扣减顺序

`daily`（签到，当日有效）/ `subscription`（月付，当期有效）/ `purchase`（永久）三列分开存；扣减顺序固定 **签到 → 月付 → 永久**（先拿会先过期的，对用户有利，也是行业惯例）。

### D3 合计由分项重算，且不开放 setter

`total` 是冗余列，但**永远由三个分项重新求和**，绝不做 `total = total - x` 的增量更新；实体的 `daily/subscription/purchase/total` 一律 `@Setter(AccessLevel.NONE)`，只能经 `spend` / `grantPurchase` / `grantSubscription` / `rollDaily` / `expireSubscription` 改动。

理由：冗余列唯一的风险就是与分项漂移；把写入路径收进实体、每次重算，这个风险在结构上归零。

### D4 有效期惰性结算，不写定时任务

`daily_date` 记签到归属的自然日，`subscription_expires_at` 记月付到期时刻；访问时判断：

- `daily_date != 今天` ⇒ 昨日签到作废，重置为今日额度并更新日期
- `subscription_expires_at` 已过 ⇒ 月付清零

好处：没有定时任务（也就没有"任务挂了积分不清零"的故障模式）、不会时区漂移、没有零点扫全表的尖峰。**日切发生在用户自己的请求里，成本为零。**

⚠️ 自然日必须显式 `ZoneId.of("Asia/Shanghai")`：生产服务器多为 UTC，用系统时区会让"一天"整体偏 8 小时。项目里已踩过一次同类坑（库里存 UTC，CLI 用 `NOW()` 插数据差 8 小时）。

### D5 并发：用户行锁，不用乐观锁重试

`SELECT ... FOR UPDATE`（`@Lock(PESSIMISTIC_WRITE)`）锁住该用户那一行，扣减、校验、日切、写流水全在锁内完成。

理由：争用范围只有**同一个用户自己的并发请求**（现实里几乎是 0）；相比乐观锁不需要重试循环，也不会在"两个请求同时花最后一分"时反复失败。余额与流水在同一事务里，要么都成功要么都不写。

### D6 幂等键 + 「先锁后查」的顺序

每笔操作带唯一键：`CONSUME:{summaryId}` / `REFUND:{summaryId}` / `ORDER:{orderId}`，唯一索引是最后一道闸。

**幂等检查必须放在拿到行锁之后**。这不是风格问题：InnoDB 默认 REPEATABLE READ 下，事务的一致性读快照在**第一次非锁定读**时建立。先查后锁的话，第二个事务的快照可能早于第一个事务提交，它会**看不到**刚写入的幂等行从而重复扣分。而 `SELECT ... FOR UPDATE` 是锁定读、不建立快照，所以"锁 → 查"的顺序能读到最新已提交状态。

### D7 签到积分额度：30 分（= 恰好一次 30 分钟视频）

`vidoc.points.daily-grant` 默认 **30**。按扣分阶梯，30 分钟视频正好 30 分 —— 每天够生成一条 30 分钟的视频，且只够一条。

| | 积分/月 | 折算时长 |
|---|---|---|
| 免费（30/天） | ≈ 900 | ≈ 15 小时 |
| 月付 ¥19.9（2000/月） | 2000 | ≈ 33 小时（**2.2×** 免费） |
| 年付 ¥189（3000/月） | 3000 | ≈ 50 小时（**3.3×** 免费） |

**这个数字必须和月付/年付的积分数一起变动**：免费额度每加 10 分/天，月付的相对价值就掉一截。

### D8 流水：不记签到 + 每用户保留 50 条

- **签到不写流水。** 它每天每人都一样、信息量为零，却是流水行数的主要来源（活跃用户 × 365/年）。砍掉它，流水从"每天必增 1 条"变成"用一次才增 1 条"。
- **每用户保留 `ledger-keep`（默认 50）条**，写入后按 `id` 倒序裁掉更旧的。

为什么是 50 而不是更小：**它是幂等键的存活窗口**（历史流水被裁掉，键也没了），也是「用户看着记录自己消失」的临界点。50 条 × ~120 字节 ≈ 6KB/用户，省下的量级是 KB，真正的收益在 D1 的物化余额和 `(user_id, id)` 索引 + LIMIT 上。

裁剪用索引区间删除（行数不足时子查询为空、比较为 NULL，命中 0 行）：
```sql
delete from points_ledger
where user_id = :userId
  and id < (select keep_id from (
      select id as keep_id from points_ledger where user_id = :userId order by id desc limit 1 offset :keep - 1
  ) t)
```
裁剪前必须先把新行 flush，否则子查询看不见它、会多删一条。

### D9 计价用固定汇率，不做逐次精算

1 积分锚定 1 分钟视频；换算成 token 时按 **1 分钟 = 175 token**（200 字/分 × 0.7 token/字 + 25% 安全边际）核定成本。

- 用户侧只按**时长**扣分，不退不补：语速差异带来的 ±40% token 波动用户不可感知，退补会显得像乱扣。
- 真实 token 只进日志，用于事后校准汇率。
- **接口绝不接受前端传金额或积分数**。

### D10 阶梯只作用于超出部分

```
d ≤ 10        : 10
10 < d ≤ 60   : 10 + (d − 10)
60 < d ≤ 180  : 60 + (d − 60) × 1.5
d > 180       : 240 + (d − 180) × 2
```

档位之间连续（60 分钟 60 分、61 分钟 62 分），避免"多一分钟贵一半"的投诉。

### D11 扣分时机：两次校验

- `SummaryService.create`：只校验**余额 ≥ 起步价 10**，不扣分 —— 余额不足时连摘要记录都不会创建。
- `SummaryProcessor` 在拿到 `duration` 后扣分；不够则终止任务并删除记录。
- 扣分后任何失败 ⇒ 原额退回（落 `purchase`，免得跨自然日退回后「刚到手就过期」）。

提交时还不知道时长（要抓元数据才知道），所以只能两段式；**不做"按预估值先扣再退补"**，那会让用户看到余额抖动。

### D12 支付搁置：只留一处接缝

不建 `orders` 表、不定义渠道接口。只提供 `PointsService.grantPurchase(userId, points, orderId)`（幂等键 `ORDER:{orderId}`），并预留 `UserPoints.grantSubscription`。支付接入时只需：建订单表 → 渠道回调验签 → 调这两个方法。

### D13 用户积分行的建立：注册时 + 启动回填 + 兜底

- 注册成功即建行（`UserService.createUser`）
- 应用启动时为存量用户批量补建（`PointsStartupBackfill`，`insert ignore ... select` 幂等）
- `PointsService.lock` 里留一条兜底补建

**为什么要三处**：`SELECT ... FOR UPDATE` 打到不存在的行会取间隙锁，两笔并发首次访问会各自拿间隙锁再各自插入，**互相死锁**。所以正常路径必须只有一条锁定读，绝不能每次先 `INSERT IGNORE` 再锁——那样在已存在的行上会取共享锁，与后续的排他锁形成同样的死锁。

### D14 前端只展示合计，但必须留一行过期提示

按用户要求，页面只出现**可用合计**，三本账的结构不出接口、不出界面。但必须保留一行「每日赠送当日有效 · 某时刻作废」：

分项对用户无感是对的；**"每天送的会过期"是用户必须知道的事实**。否则他昨天有 50 分、今天变 20 分，会认为系统吃了他 30 分。这不是展示内部结构，是告知规则。

前端两次请求（余额、流水）**串行**发出：两者都会触发签到到账，串行可避开同一用户的首次并发建行。
