## Context

动机见 `proposal.md - Why`。影响方案的现状约束：

- 鉴权是**纯请求头**的（`sa-token.is-read-cookie: false`，`token-name: Authorization`），所以浏览器原生表单提交带不上身份 —— 这决定了"发起支付"不能是一个让浏览器直接导航过去的受保护 GET 端点。
- `SaTokenConfigure` 目前只放行 `/api/auth/**`，其余 `/api/**` 一律要求登录。支付宝的异步通知是匿名 POST。
- `points` 能力已把余额**物化**成 `user_points` 一行，并明确规定"余额查询与流水条数无关"（见 `openspec/specs/points/spec.md`）。任何新状态都不能破坏这条。
- `UserPoints` 的变更字段**一律不开 setter**，只能经 `spend` / `grantPurchase` / `grantSubscription` / `rollDaily` / `expireSubscription`。`grantSubscription(points, expiresAt)` 现有语义是"覆盖上一期"，注释里写着"当前无调用方（支付模块未接）"。
- 支付宝给的是**页面跳转式**收单：下单接口返回自动提交的 `<form>` 而非 JSON；同步跳转不可信。

## Goals / Non-Goals

**Goals:**

- 一次付款端到端可用：下单 → 跳转支付宝 → 付款 → 通知回站 → 积分到账。
- 支付结果**只能**由验签后的异步通知或主动查询确认，且重复通知不重复发放。
- 订阅额度按期滴灌，且不引入定时任务（沿用惰性结算）。
- 金额与额度只由服务端套餐定义决定。

**Non-Goals:**

- 退款、对账单下载、关闭交易接口（本期不做）。
- 自动续费（需另开「周期扣款」产品）。
- 多支付渠道抽象层：本期只有支付宝一家，不做 provider 接口与工厂。

## Decisions

### 1. 独立 `orders` 表，不复用 `user_points`

字段：`id` / `out_trade_no`（唯一）/ `user_id` / `plan_code` / `amount` / `periods` / `period_points` / `status` / `alipay_trade_no` / `paid_at` / `expire_at` / `created_at`。

**备选**：把支付宝交易号塞进 `user_points`、用"套餐 + 时间"反推订单。否决 —— 拿不到幂等键，也没法承载"这笔订单买到几期"。

`out_trade_no` 用 UUIDv7 的 32 位十六进制（去横线）：全局唯一、不可猜、时间有序（与摘要的 `public_id` 同源思路），且满足支付宝对订单号的字符与长度要求。

### 2. 发起支付 = 后端返回表单 HTML，前端写入新标签页

调用 `alipay.trade.page.pay`（`product_code = FAST_INSTANT_TRADE_PAY`），SDK 的 `pageExecute(request, "POST")` 拿到自提交表单的 HTML 字符串，作为 JSON 字段返回给前端；前端**先同步** `window.open('', '_blank')` 占住窗口（否则异步回来后会被弹窗拦截），拿到 HTML 后写进去，表单自动提交跳转收银台。

**备选**：(a) 后端直接以 `text/html` 返回、前端 `location.href` 导航过去 —— 需要 Authorization 头，浏览器导航带不了，除非再引入一次性换取令牌，复杂度不值。(b) 前端解析表单字段自己重建 —— 依赖 SDK 输出结构，脆弱。选 (a) 的变体即当前方案。

### 3. 通知端点匿名 + 安全边界完全靠验签

`POST /api/payments/alipay/notify` 加入 `SaTokenConfigure` 的放行名单。放行不等于不设防：验签（支付宝公钥）+ 核对 `app_id` / `out_trade_no` / `total_amount` 就是这一层的全部安全性，缺一不可。

端点以 `text/plain` 返回字面量 `success` / `failure` —— 支付宝按响应体判断是否重投，返回 JSON 会被判为失败。

### 4. 幂等靠订单状态机，不靠额外的去重表

`status` 为 `PENDING → PAID`（或 `→ CLOSED`）。通知处理在**行锁**内读取订单，只有当前状态为 `PENDING` 且交易状态为支付成功时才跃迁并发积分；已是 `PAID` 直接回 `success`。这与 `points` 已有的"锁定读 → 锁后查幂等"是同一套路数。

**备选**：按 `alipay_trade_no` 建唯一索引去重。冗余 —— 订单号本身就是唯一键，状态机足够。

### 5. 订阅滴灌的状态物化在 `user_points`，不加定时任务

`user_points` 增加两个字段：`subscription_period_points`（每期额度）与 `subscription_periods_left`（含当前期在内的剩余期数）；复用已有的 `subscription_expires_at` 表示**当前期**的结束时刻。

惰性结算：在现有的 `expireSubscription` 位置，当 `now > subscription_expires_at` 时循环推进 —— 每推进一期就 `periods_left--` 并把 `expires_at` 加一个周期，直到 `periods_left == 0`（清零订阅）或 `expires_at` 落在未来（此时该期额度立即到账）。跨越多个未访问期数时这会循环若干次，上限就是所购期数（≤12）。

**备选**：把期数进度记在 `orders` 上。否决 —— 余额查询要变成"读一行 + 查订单"，破坏那条"与流水条数无关"的 O(1) 约束。

周期长度：月付 30 天、年付按 365/12 ≈ 30.4 天。**不用自然月**（自然月长度不一，跨月推进会让"12 期"落不到 365 天上），改用固定天数，误差落在购买日附近，可接受。

### 6. 两种商品：订阅（限时积分）与充值（永久积分）

`Plan` 从「只有订阅档」扩成两类，用一个 `kind` 字段区分，**不新建第二套枚举或第二张表** —— 两者在支付宝侧是同一种收单（电脑网站支付、同一个异步通知端点、同一个 `orders` 表、同一个状态机），差别只在"确认支付后往哪个积分桶里放"。既然 `orders` 已经存了 `plan_code`，商品类型可以从 `Plan.of(planCode)` 反推，**不加列、不改表**。

| | 订阅 | 充值 |
|---|---|---|
| 积分桶 | `SUBSCRIPTION`（限时，每期到期作废） | `PURCHASE`（永久） |
| 发放 | 一次付款分 N 期滴灌 | 一次性全额到账 |
| 生效期内 | **拒绝再买**（见第 6 条） | **随时可买** |
| 发放入口 | `PointsService.grantSubscription(plan, orderId)` | `PointsService.grantPurchase(points, orderId)`（09-24 就留好的接缝，`orderId` 第一次有来源） |

下单时的拦截因此变成 `plan.getKind() == SUBSCRIPTION && points.hasActiveSubscription(userId)` —— 这是**唯一**需要区分商品类型的地方（外加 `confirmPaid` 的发放分支）。

**定价原则（用户 2026-09-26 指定）**：像手机流量套餐一样，**单独买一定更贵**。订阅是打包价（月付 ￥19.9 / 2000 分 ≈ **100 分/元**，年付 ￥189 / 36000 分 ≈ **190 分/元**），充值按 **50 / 60 / 70 分每元**递阶。永久积分单价比限时更低是**故意**的 —— 否则没人会买会过期的订阅。三档的递增幅度（50→60→70）用来表达"多买划算"，而不是靠折扣话术。定价的唯一真源仍是 `Plan` 枚举，改价要连 `app/utils/plans.ts` 一起改。

### 7. 订阅生效期内拒绝再次购买订阅

新的订阅付款会**覆盖**订阅状态（首期立即到账、剩余期数 = 期数 − 1）。为了不让覆盖吞掉已付时长，下单时校验：当前订阅仍在有效期内 → 拒绝订阅类套餐的下单，返回可读错误。到期后再买，覆盖永远发生在订阅已耗尽时。

**备选**：允许叠加（期数累加）。否决 —— 月付 2000/期与年付 3000/期的每期额度不同，叠加后"剩余期数 × 每期额度"要么算错要么需要分档存，为一个边缘场景引入分档不值。

这条直接对应 `specs/payment/spec.md` 里"订阅生效期内重复购买"场景，不是纯实现细节。前端据此置灰购买入口，靠 `GET /api/payments/subscription` 只回一个布尔值 —— 订阅额度与到期时刻属于 `points` 的账内信息，`points` 的 spec 明确不许出接口，所以这个判断放在支付能力里问。

## Risks / Trade-offs

- **签名模式选了公钥模式（不带证书）** → 文档提示"涉及资金支出的接口必须用证书加签"。本期只收款不支出，公钥模式可行；**将来加退款时可能需要切到证书模式**（要额外引入 bcprov / commons-logging / fastjson 三个包）。
- **覆盖式订阅会吞掉已付时长** → 已用"生效期内拒绝再买"堵住；若将来要做"续费叠加"，需要重构第 5 条的存储（每期额度要分档）。
- **固定 30 天周期与自然月不符** → 用户感知是"每月差不多同一天到账"，误差一天以内；换取的是判定逻辑简单且能精确合成 365 天。
- **永久积分单价低于限时积分** → 这是刻意的（见第 6 条）：充值每元 50~70 分，订阅每元 100~190 分。风险是"充值的性价比可能好到没人订阅" —— 实际不会，因为限时积分是**按月**给的额度，而充值是一次性买断、总价更高才能堆出同等积分。**调整时唯一要守的约束是「充值 ≤ 订阅的单位积分」**，破了就没人订阅了。
- **异步通知可能丢失** → 有主动查询兜底；且用户从收银台返回时前端会主动查一次。
- **`ddl-auto: update` 只加列不删列** → `user_points` 新增两列可直接靠它补；但 `orders` 是新表，`db/schema.sql` 必须同步更新（新环境建库的唯一依据）。
- **沙箱只支持余额支付** → 沙箱能验通的路径比线上窄；真实支付方式必须在线上用小额订单验收。
- **通知端点匿名暴露** → 最大的攻击面就在这里。验签失败必须**在动任何业务数据之前**返回，且失败要记日志（否则被刷时无从排查）。
- **弹窗拦截** → 前端必须先同步 `window.open` 再发请求；若仍被拦，需要回退到"当前页跳转"的降级路径。

## Migration Plan

1. **支付宝侧（人工，可并行）**：创建网页应用 → 配置 RSA2 公钥加签 → **应用网关填 `https://vidocnote.com/api/payments/alipay/notify`** → 提交上线审核（约 1 个工作日）→ 绑定商家账号 → 开通「电脑网站支付」。
2. **代码**：加 SDK 依赖 → `orders` 表（`schema.sql` + `ddl-auto`）→ `user_points` 两列 → 配置项 → 订单服务/支付宝服务/控制器 → 放行通知路径 → 前端下单与订单列表。
3. **配置**：APPID、应用私钥、支付宝公钥、网关地址、沙箱开关全部走环境变量，**不入库**；`.env.example` 补占位符。
4. **联调**：先沙箱验证"下单 → 表单 → 余额付款 → 通知 → 到账"，再切线上用小额订单验收真实支付方式。
5. **回滚**：配置项 `vidoc.payment.enabled` 关闭时，下单接口返回 503 且前端隐藏购买入口；已支付订单的积分不受影响（数据已落库，无半成品状态）。
